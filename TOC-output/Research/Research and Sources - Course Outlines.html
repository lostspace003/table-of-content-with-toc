Credential and Access Management Automation with Claude

  • Module 2: joiner access requests via ServiceNow Service Catalog REST API. The Service Catalog API lives under the sn_sc namespace at /api/sn_sc/servicecatalog/; POST items/{sys_id}/order_now orders an item directly (sysparm_quantity is required, with optional variables and sysparm_requested_for) and returns the resulting sc_request number and sys_id, while POST cart/submit_order checks out the cart and behaves differently under one-step vs two-step checkout. [1]
  • Module 2: raising access requests through Jira Service Management. POST /rest/servicedeskapi/request creates a customer request; the body must include serviceDeskId, requestTypeId and requestFieldValues covering every field the request type requires, needs the write:servicedesk-request scope, and returns 201 Created with the request object. [2]
  • Module 3: joiner provisioning in Microsoft Entra ID via Microsoft Graph. POST /users creates an Entra ID user and requires accountEnabled, displayName, mailNickname, passwordProfile and userPrincipalName; the least-privileged permission for both delegated and application calls is User.Create, with User.ReadWrite.All and Directory.ReadWrite.All listed only as higher-privileged alternatives. [3]
  • Module 3: mover workflows - group membership changes via Microsoft Graph. POST /groups/{group-id}/members/$ref adds one member with an @odata.id reference and PATCH /groups/{group-id} with members@odata.bind adds up to 20 at once; GroupMember.ReadWrite.All is the least-privileged permission, and newly created groups may briefly return 400 due to directory replication delay, so callers should retry after a short wait. [4]
  • Module 4: short-lived credentials and leaver revocation with HashiCorp Vault. Vault attaches a lease with a TTL to every dynamic secret and service token; consumers must renew before expiry or the secret is automatically revoked, and revoking a lease (or a token, which revokes all leases it created, or an entire path prefix) invalidates the credential immediately, e.g. deleting the AWS access keys it issued. [5]
  • Module 5: least-privilege design for automated access grants. NIST defines least privilege (per CNSSI 4009-2022, SP 800-53 Rev. 5 and SP 800-171r3) as restricting each user, process or entity to the minimum set of system resources and authorizations needed to perform its assigned function. [6]
  • Module 6: never placing secrets in LLM prompts (OWASP LLM Top 10). OWASP lists security credentials among the sensitive data an LLM application can leak through its outputs, and recommends input validation and redaction before data reaches the model, least-privilege access, and tokenizing or masking sensitive content, warning that system-prompt restrictions alone can be bypassed via prompt injection. [7]
  • Module 6: secure MCP tool design for Claude-driven provisioning agents. The MCP spec forbids token passthrough: an MCP server MUST NOT accept or forward tokens that were not explicitly issued to it, and it recommends a progressive least-privilege scope model that starts with minimal scopes and elevates via targeted WWW-Authenticate challenges rather than granting omnibus scopes up front. [8]
  • Module 6: hardening a Claude agent that touches identity systems. Anthropic states it does not security-audit or manage any MCP server and advises writing your own or using trusted providers with per-server permissions; it also recommends not piping untrusted content directly to Claude, reviewing commands before approval, and notes API keys and tokens are kept in the OS keychain or a 0600-mode file rather than in prompts. [9]

Cisco ACI Upgrade Automation with Claude

  • Course foundation: primary upgrade/downgrade reference guide. The guide is organized into an ACI Firmware Upgrade Overview, an Upgrade/Downgrade Architecture chapter, Pre-Upgrade/Downgrade Checklists, mixed-version operation guidance, and per-interface procedures (GUI by release, REST API, CLI). [10]
  • Module: end-to-end upgrade workflow and order (APIC cluster first, then switches). Cisco's workflow upgrades the APICs first (after backup, image download, pre-upgrade validation and HUU/CIMC updates), then re-runs validations and upgrades the ACI-mode switches only once the APIC cluster is Fully Fit; multistep upgrades repeat the cycle through an intermediate release. [11]
  • Module: designing switch update groups. Split leaf and spine switches into at least two update groups (e.g. ODD/EVEN) so that one member of every vPC pair, one APIC-connected leaf, and at least one route-reflector and IPN-connected spine per pod stay up; from APIC 4.2(5) the default concurrent capacity per group is unlimited, so Cisco recommends separate groups for scheduling. [12]
  • Module: pre-upgrade validation (built-in validator vs standalone script). Three validation options exist: the built-in Pre-Upgrade Validator that runs automatically when an update group is configured, the now-obsolete App Center app (App Center deprecated in 6.1.2), and the standalone script run from the APIC CLI; Cisco advises running the script at least two weeks before the maintenance window, and from APIC 6.2(1) the script's external rules can be pulled into the Upgrade GUI via Intersight or manual download. [13]
  • Module: running and parsing the Pre-Upgrade Validation script with Claude. The script is copied to /data/techsupport on an APIC, run with Python using admin credentials against a target version already present on the APIC, and reports each check as PASS, FAIL or MANUAL CHECK REQUIRED with a recommended action for each FAIL and a summary count by status. [14]
  • Module: validation reference and automating check triage. The example output lists 47 checks (image/MD5, APIC cluster fitness, CIMC compatibility, SSD health, NTP, bootflash, overlapping VLAN pools, vPC pairing, L3Out MTU, ISIS metric for Multi-Pod) and the script saves results plus debug data in a .tgz bundle that can be attached to a TAC case. [15]
  • Module: driving the APIC upgrade via REST API. A controller upgrade via REST is three POSTs: register the image source with firmwareRepoP/firmwareOSource at /api/node/mo/uni/fabric.xml, set the target version with firmwareCtrlrFwP at /api/node/mo/uni/controller.xml, then trigger it with maintCtrlrMaintP adminState="up" adminSt="triggered". [16]
  • Module: APIC REST API authentication and session handling for automation. Clients POST to aaaLogin (prefixing the username with apic:domain\ when multiple login domains exist), receive a token in the APIC-cookie Set-Cookie header and aaaLogin token attribute with a default refreshTimeoutSeconds of 600, and must call aaaRefresh before expiry, storing the new token returned on every refresh. [17]
  • Module: reading release notes and compatibility matrices before a target version is chosen. Release 6.1(4h) became available on August 13, 2025; the notes instruct installing only the CIMC versions listed in the compatibility table and reviewing software advisory CSCwo74485 for UCS C225 M6 (APIC-L4/M4) servers before upgrading, alongside new features such as virtual APIC on Nutanix AHV and TACACS+ over TLS. [18]

Bill Creation Automation with Claude

  • Module 1: GST tax invoice vs bill of supply and Rule 46 mandatory fields. GST law prescribes no fixed invoice layout, but Rule 46 of the CGST Rules 2017 makes a set of fields mandatory; a registered person making taxable supplies issues a tax invoice, while composition dealers or exempt-only suppliers issue a bill of supply, and no invoice is needed for supplies under Rs. 200 subject to conditions. [19]
  • Module 2: pulling vendor bills from an Outlook/M365 mailbox via Graph. GET /me/messages (or /users/{id}/messages) returns 10 messages per page by default, $top can raise it to 1000, Mail.ReadBasic is the least-privileged permission, and paging must follow the @odata.nextLink URL rather than hand-building $skip values. [20]
  • Module 2: reading a single bill email body as plain text or raw MIME. GET /me/messages/{id} returns the message object; appending /$value returns the raw MIME content instead, and sending Prefer: outlook.body-content-type="text" returns the body as plain text rather than the default HTML. [21]
  • Module 2: finding invoice emails in Gmail with search queries. messages.list returns only message IDs and thread IDs, so each message must then be fetched with messages.get; the q parameter accepts Gmail search syntax such as from:someuser@example.com is:unread to narrow results. [22]
  • Module 2: downloading PDF bill attachments from Gmail. Attachments are fetched with a GET on users/{userId}/messages/{messageId}/attachments/{id} with an empty request body, returning the attachment data for downstream extraction. [23]
  • Module 3: sending supplier invoice PDFs to Claude for extraction. Claude accepts standard unencrypted PDFs up to 32 MB per request and up to 600 pages (100 pages when the context window is under 1M tokens), and can read text, tables and charts to convert them into structured data. [24]
  • Module 3: schema-constrained JSON for invoice line items, GSTIN and tax totals. Setting output_config.format to type json_schema with a schema constrains Claude's response to that schema so it can be parsed without retry loops; output may still diverge only on refusals (stop_reason refusal) or max_tokens truncation, and the older output_format parameter is deprecated. [25]
  • Module 4: rendering the HTML bill template to a PDF file. page.pdf() renders the page using the print CSS media type, so colours are adjusted for printing by default; call page.emulateMediaType('screen') first to render the on-screen styling instead. [26]

Certificate Renewal Automation with Claude

  • Module: F5 BIG-IP certificate install via iControl REST. The /mgmt/tm/sys/file/ssl-cert collection supports GET; individual certificate resources support GET, POST, PUT, PATCH and DELETE, are keyed by name, partition and subPath, and take an optional sourcePath property that names the URI the certificate file is copied from. [27]
  • Module: NetScaler certificate install via NITRO API. Creating a certificate-key pair is a POST to /nitro/v1/config/sslcertkey with a JSON body whose mandatory fields are certkey and cert (paths point to files on the appliance disk, typically /nsconfig/ssl); a successful add returns 201, and UPDATE is a PUT to the same URL with certkey mandatory and optional fields such as expirymonitor and notificationperiod. [28]
  • Module: NetScaler certificate binding to SSL vservers. After installing the cert and key under /nsconfig/ssl you run add ssl certKey <name> -cert <file> -key <file> (optionally -expiryMonitor ENABLED -notificationPeriod <days>), link any intermediate certificates first, then bind with bind ssl vserver <vs> -certkeyName <name> and verify with show ssl vserver; every SSL virtual server needs its own valid binding. [29]
  • Module: Radware Alteon certificate management. On Alteon the installation flow is to build one PEM file with the server certificate followed by the intermediate chain, enter the cfg then cert menu on the switch CLI, paste the PEM, terminate the input with three periods, and then run apply to activate the change (no official Radware public page could be fetched, so this CA guide is the best available source). [30]
  • Module: ACME and internal CA renewal workflow. ACME replaces manual Web PKI steps with machine-readable exchanges: a client creates an account, submits an order for identifiers, satisfies one of the challenges offered in each authorization to prove control, finalizes the order with a CSR and then downloads the issued certificate; the protocol also covers revocation. [31]
  • Module: OpenSSL verification of installed chains. openssl verify validates certificate chains and tries to report every problem it finds rather than stopping at the first; -CAfile supplies trusted anchors while -untrusted (repeatable) supplies intermediates used only for chain building, not as trust anchors. [32]
  • Module: building an MCP server for load balancer APIs. MCP is an open-source standard, likened to a USB-C port for AI applications, that lets AI apps connect to data sources, tools and workflows in a uniform way; it is supported by Claude, ChatGPT, VS Code, Cursor and others so a server built once works across clients. [33]
  • Module: orchestrating renewals with Claude Code. Claude Code is an agentic coding tool available in terminal, IDE, desktop app and browser; it can be scripted non-interactively with claude -p for piping and CI use, connects to external systems through MCP, supports hooks that run shell commands before or after its actions, and can run cloud or desktop scheduled tasks for recurring work. [34]
  • Module: building a renewal agent with the Claude Agent SDK. The Agent SDK exposes the same tools, agent loop and context management as Claude Code as a Python or TypeScript library, with built-in tools, hooks, subagents, MCP connections, permission controls, resumable sessions, skills and plugins; third-party products must use API-key authentication rather than claude.ai logins. [35]

Configuration Comparison Automation with Claude

  • Module 1: parsing BIG-IP virtual server objects from bigip.conf / tmsh list. A BIG-IP virtual server is defined by properties such as destination (address:port), pool, profiles, persist, rules, policies, vlans and source-address-translation; `list virtual` prints the configuration while `show virtual` adds runtime statistics, and the older snat/snatpool options are deprecated in favor of source-address-translation. [36]
  • Module 2: extracting and diffing NetScaler ns.conf (running vs saved config). NetScaler stores its saved configuration in /nsconfig/ns.conf; `save ns config` persists changes, `show ns runningConfig` and `show ns ns.conf` display running and saved config, and the built-in `diff ns config <file1> <file2>` command (or GUI Configuration difference) compares two configuration files. [37]
  • Module 5: NetScaler config converter and instance-to-instance migration. The Configuration Builder accepts a live instance, pasted ns.conf CLI commands, or an uploaded config file, generates a StyleBook plus a reusable config pack for migrating to other instances, and does not detect named expressions or responder HTML pages, which must be pre-created on the target. [38]
  • Module 3: mapping ADC objects to AWS ELB listeners, rules and target groups. An ALB is composed of listeners (protocol/port), listener rules (priority, conditions, actions, with a mandatory default rule) and target groups that route to registered targets with per-target-group health checks; a target may belong to multiple target groups and the default routing algorithm is round robin. [39]
  • Module 3: mapping ADC objects to Azure Application Gateway components. Azure Application Gateway routes traffic through frontend IPs, listeners (basic or multi-site, up to 5 host names each), request routing rules (basic or path-based, one listener per rule), HTTP/backend settings, backend pools and health probes; HTTP/2 is client-side only and backend communication is always HTTP/1.1. [40]
  • Module 4: F5 migration tooling, converting imperative config to AS3/DO declarations. BIG-IP ACC converts existing BIG-IP configuration files into declarative AS3 (application/service) or Declarative Onboarding (system, network, clustering) JSON declarations, and is a community-supported tool whose source and issue tracker live on GitHub. [41]
  • Module 4: F5 Journeys UCS-based version and platform migration. F5 Journeys (successor to the BIG-IP Migration Assistant, code at github.com/f5devcentral/f5-journeys) accepts or generates a UCS archive, migrates full configurations from 11.5.0+ to newer releases including VELOS and rSeries, flags feature-parity gaps with built-in fixes, and can extract individual applications into AS3. [42]
  • Module 6: building a Claude-driven comparison agent with tool calls. To let Claude invoke a custom function (for example a config parser or diff tool), you pass a tool with a JSON input_schema; Claude responds with stop_reason tool_use and a tool_use block, your code executes it and returns a tool_result block, and `strict: true` guarantees calls conform to the schema. [43]
  • Module 7: semantic diff approaches and drift detection patterns. terraform plan refreshes state, compares desired configuration against prior state and reports a semantic diff using + create, - destroy, ~ update in-place and -/+ replace markers, with -detailed-exitcode returning 0 (no changes), 1 (error) or 2 (changes present) for automation pipelines. [44]

Traffic and Flow Diagram Automation with Claude

  • Module 1: traceroute fundamentals and the IP Traceroute option. Classic TTL-based traceroute needs roughly 2n packets for n hops; RFC 1393 proposed an IP Traceroute option plus an ICMP Traceroute message (type 30) so each router reports back directly, cutting this to about n+1 packets and avoiding mid-trace path shifts. It is Experimental and was later obsoleted by RFC 6814. [45]
  • Module 1: ping fundamentals (ICMP Echo/Echo Reply) and Time Exceeded. ICMP Echo is type 8 and Echo Reply is type 0, with identifier and sequence fields used to match replies to requests and the received data echoed back unchanged; Time Exceeded is type 11, with code 0 meaning TTL exceeded in transit, which is the message traceroute relies on. [46]
  • Module 1: how traceroute probes work on Cisco IOS, Linux and Windows. Cisco IOS and Linux traceroute send UDP probes starting at destination port 33434 with TTL starting at 1 (default max 30 hops); each hop returns ICMP Time Exceeded (type 11, code 0) and the destination returns ICMP Port Unreachable (type 3, code 3). Windows tracert uses ICMP Echo instead, and Cisco routers rate-limit ICMP unreachables (default one per 500 ms), which can show up as missing hops. [47]
  • Module 2: continuous path measurement with mtr. mtr combines traceroute and ping in one tool: it sends probes with successively larger TTL values to discover the path and then prints running per-hop statistics. The README warns that routers may not respond to or may rate-limit ICMP, so apparent loss at an intermediate hop does not necessarily mean forwarded traffic is being dropped there. [48]
  • Module 3: Mermaid flowchart syntax for network path diagrams. Flowcharts start with `flowchart` (or `graph`) plus a direction keyword (TB/TD, BT, RL, LR); edges include `-->`, `---`, dotted `-.-`, thick `===`, and `--o`/`--x`; `subgraph id [Title] ... end` groups nodes and can carry its own direction; from v11.3.0 shapes can be set with `A@{ shape: ... }`. A lowercase `end` inside a node label breaks the diagram. [49]
  • Module 3: rendering Claude-generated Mermaid in GitHub Markdown. GitHub renders a Mermaid diagram from a fenced code block labeled `mermaid` in issues, discussions, pull requests, wikis and Markdown files; placing `info` in a mermaid block reveals which Mermaid version GitHub is running. [50]
  • Module 4: draw.io CSV import for automated topology diagrams. Via Arrange > Insert > Advanced > CSV, configuration lines starting with `#` precede the CSV data; `# label:` builds shape text from `%column%` placeholders, `# connect:` takes a JSON object with `from`/`to` columns (plus label, style, invert), `# identity:` lets a re-import update existing shapes instead of duplicating them, and `# layout: auto` with spacing keys applies an automatic layout. [51]
  • Module 4: Graphviz DOT for programmatic path graphs. A DOT file declares `graph` (undirected, edges `--`) or `digraph` (directed, edges `->`), optionally prefixed with `strict` to forbid duplicate edges; attributes are `key=value` pairs in square brackets, `graph`/`node`/`edge` statements set defaults only for objects defined afterwards, and subgraph names beginning with `cluster` are drawn as grouped bounding boxes by some layout engines. [52]
  • Module 5: prompting Claude to emit clean Mermaid/DOT output. To control output format, tell Claude what to do rather than what not to do, wrap content types in XML tags (e.g. instructions, context, input) to reduce misinterpretation, and use XML format indicators or structured outputs/tool calling for a fixed structure; the page also notes that few-shot examples are one of the most reliable ways to steer output format and structure. [53]

Device Health Monitoring Automation with Claude

  • Module: NetScaler virtual server health via NITRO stat API. GET /nitro/v1/stat/lbvserver (or /lbvserver/<name>) returns per-vserver state values such as UP(7), DOWN(1), OFS(4), TROFS(5), plus vslbhealth (percentage of bound services that are UP), actsvcs and totalrequests. [54]
  • Module: NetScaler HA pair and config-sync status checks. GET /nitro/v1/stat/hanode exposes hacurmasterstate (PRIMARY/SECONDARY/CLAIMING/FORCE CHANGE), hacurstate (UP, DISABLED, PARTIALFAIL, COMPLETEFAIL, etc.) and haerrsyncfailure, a counter of failed primary/secondary config syncs since the last transition, commonly caused by an RPC password mismatch. [55]
  • Module: F5 BIG-IP polling via iControl REST. iControl REST is the REST successor to the SOAP iControl framework; anything doable from the BIG-IP command line can be done programmatically, with LTM objects such as pools reached under /mgmt/tm/ltm/ (example: POST to /mgmt/tm/ltm/pool with basic-auth credentials). [56]
  • Module: interpreting F5 pool member state/session fields. Pool member objects expose a state field (user-down forces the member offline overriding monitors; user-up returns it to its monitor-derived state), a session field (default user-enabled, controlling new sessions) and a monitor field listing assigned health monitors and their status. [57]
  • Module: ServiceNow incident creation via Table API. POST /now/table/{tableName} inserts exactly one record (bulk insert not supported), accepts JSON or XML bodies via Content-Type, returns 201 with a Location header for the new record, and the calling user must hold roles sufficient to access the target table; an example posts short_description, assignment_group, urgency and impact to incident. [58]
  • Module: hands-on lab creating an incident from a health-check failure. The walkthrough POSTs to https://instance.service-now.com/api/now/v1/table/incident with a body like {"short_description":"...","comments":"..."}; it requires the admin, web_service_admin or rest_api_explorer role and the response includes a Location header pointing at the new incident. [59]
  • Module: scheduling health checks with GitHub Actions cron. The schedule event uses five-field POSIX cron in UTC (a time zone can be set), minimum interval is every 5 minutes, runs only from the default branch, can be delayed at the top of the hour under load, and scheduled workflows in public repos are auto-disabled after 60 days of inactivity. [60]
  • Module: orchestrating device checks and ticketing with a Claude agent. The Claude Agent SDK, available in Python and TypeScript, runs the same agent loop as Claude Code with built-in tools (file read/write, run commands, web search), hooks, subagents, permissions, sessions and MCP support for connecting external tools and data sources. [61]
  • Module: Radware Alteon monitoring and REST API reference pointer. Radware's official Alteon documentation set includes a dedicated 'Alteon REST API User Guide' alongside the Command Reference, CLI Application Guide and Troubleshooting Guide, which are the primary references for programmatic status and uptime checks on Alteon ADCs. [62]

HR Hiring Flow Automation with Claude

  • Module 2: exporting candidates and applications from an ATS via API. Harvest was built so customers can export their Greenhouse data; it uses Basic Auth over HTTPS with the API token as the username and blank password, exposes list/retrieve/add/edit/anonymize endpoints for candidates and advance/move/reject/hire endpoints for applications, and Harvest v1/v2 is deprecated for removal on 31 August 2026 in favour of v3. [63]
  • Module 2: pulling candidate pipeline data from Lever. The Lever Data API is JSON over HTTPS at https://api.lever.co/v1, authenticates with Basic Auth API keys or OAuth 2.0 (access tokens expire after one hour), is rate limited to 10 requests/second per key with bursts to 20, and the Candidates endpoints are deprecated since 2020 in favour of Opportunities. [64]
  • Module 2: LinkedIn Talent API integration options for an ATS. LinkedIn Talent Solutions offers partner-facing APIs grouped as Apply Connect, Apply with LinkedIn, Job Posting API, CRM Connect and Recruiter System Connect; Recruiter System Connect synchronises candidate information between an ATS and LinkedIn Recruiter, while the Job Posting API ingests jobs already created in an ATS or job board. [65]
  • Module 2: Naukri job-posting integration and its access constraints. Naukri has no self-serve developer portal: an employer must request its team's API key from its Naukri point of contact, Naukri requires a paid subscription to post jobs (which may cap active postings), and postings fail unless location, experience range and job role are present and correctly formatted. [66]
  • Module 5: lawful basis, notice and consent for candidate data under DPDP Act 2023. Section 5 requires every consent request to be accompanied or preceded by a notice stating the personal data and purpose, how to exercise rights and how to complain to the Board; Section 6 requires consent to be free, specific, informed, unconditional and unambiguous with a clear affirmative action; and Section 7(i) lists processing for the purposes of employment as a 'certain legitimate use' that does not require consent. [67]
  • Module 5: compliance timeline, consent notices, breach notification and penalties. The DPDP Rules, 2025 were notified on 14 November 2025 with an eighteen-month phased compliance period; every Data Fiduciary must issue a separate, clear, purpose-specific consent notice, Consent Managers must be India-based companies, breaches must be reported to affected individuals and the Data Protection Board, and penalties run up to Rs 250 crore for failing to maintain reasonable security safeguards. [68]
  • Module 3: scoring candidate English proficiency on the CEFR scale. CEFR has six levels grouped into three bands: Basic user (A1 Breakthrough, A2 Waystage), Independent user (B1 Threshold, B2 Vantage) and Proficient user (C1 Effective operational proficiency, C2 Mastery); B2 is where a candidate can follow complex technical text in their field and converse fluently with native speakers, and levels can be subdivided locally (for example A1.1/A1.2). [69]
  • Module 4: schema-constrained screening output from Claude. Passing output_config.format with type json_schema makes Claude return JSON that matches the schema (no beta header needed; the older output_format parameter is deprecated); objects must set additionalProperties:false, recursive schemas and numeric min/max constraints are unsupported, and strict:true on a tool can be combined in the same request, with schemas cached for 24 hours so sensitive data must not be put in schema definitions. [70]
  • Module 4: wiring ATS and portal APIs to Claude as tools. A client tool is defined with a name, description and JSON input_schema; Claude answers with stop_reason tool_use and a tool_use block, the application runs the call and returns a tool_result block in the next user turn, and tool_choice (auto by default, with disable_parallel_tool_use available) controls whether and how Claude must call a tool, while strict:true guarantees the inputs match the schema. [71]

Terraform and GitHub Automation with Claude

  • Module 1: Terraform fundamentals - state and common mistakes. Terraform maps real infrastructure to configuration through state stored per workspace; state is a JSON file that should not be hand-edited or committed to version control, and HashiCorp recommends a remote backend or HCP Terraform instead of the default local file. [72]
  • Module 1: remote backends and shared state. A configuration may contain only one backend block; backend settings are written in plain text to .terraform/terraform.tfstate and plan files, so credentials should be supplied via environment variables rather than in the configuration. [73]
  • Module 1: Terraform modules. A module is a collection of resources Terraform manages together; modules can be sourced from the local filesystem, a Terraform registry, or VCS repositories, and Terraform downloads registry modules automatically when source and version are set in a module block. [74]
  • Module 1: terraform fmt/validate in CI. terraform fmt rewrites files to a single canonical style with no customization options; the -check flag returns a non-zero exit status when files are not formatted, and -recursive is needed to process subdirectories, which makes it suitable as a CI gate. [75]
  • Module 2: branches, pull requests and branch protection rules. Branch protection rules can require passing status checks or a linear history before pushes, block force pushes and deletions by default, and do not apply to admins unless 'Do not allow bypassing the above settings' is enabled; only one branch protection rule applies to a branch at a time, a limitation rulesets do not share. [76]
  • Module 2: CODEOWNERS for Terraform review ownership. A CODEOWNERS file placed in .github/, the repo root, or docs/ automatically requests review from the listed owners when a PR touches their files; the file on the PR's base branch is used, owners must have write access, invalid lines are skipped, and files over 3 MB are not loaded. [77]
  • Module 3: GitHub Actions workflows for Terraform plan/apply. The reference workflow runs terraform plan on every commit to a pull request branch so changes can be reviewed before merge, then runs apply when the PR is merged to main; it authenticates to HCP Terraform with a team token stored as the TF_API_TOKEN GitHub secret. [78]
  • Module 4: F5 BIG-IP Terraform provider and AS3 declarations. The bigip_as3 resource takes a required as3_json argument pointing to an AS3 declaration file and an optional tenant_filter that restricts changes to a single tenant; it requires BIG-IP 12.1.x or later, AS3 extension 3.10 or later, and an Administrator-role account. [79]
  • Module 5: Claude Code GitHub Actions for Terraform PR automation. The anthropics/claude-code-action runs in interactive mode (responding to @claude mentions in issues and PRs) when no prompt input is given, or in automation mode on any GitHub event when a prompt is supplied; it authenticates via an ANTHROPIC_API_KEY or CLAUDE_CODE_OAUTH_TOKEN secret, requires the triggering user to have write access, and rejects bot actors unless listed in allowed_bots. [80]

Troubleshooting Automation with Claude

  • Module: creating and updating incidents via the ServiceNow Table API. The Table API exposes CRUD endpoints under /now/table/{tableName}: GET lists or reads records, POST inserts a single record (no bulk insert), PATCH/PUT update by sys_id, and DELETE returns HTTP 204 on success; a versioned path /api/now/{api_version}/table/... is optional and defaults to the latest version. [81]
  • Module: incident email notifications and acknowledgement replies. Every outbound notification carries a watermark label that lets ServiceNow match an inbound reply back to the originating record, and inbound email actions define how those replies (for example an acknowledgement) are processed; notifications can also be batched into digests over a time interval. Agentic Virtual Patching Platform

  • Module 1: virtual patching lifecycle and best practices. [97]
  • Module 2: OWASP CRS anomaly scoring and paranoia levels. CRS separates detection from blocking: each matching rule adds points by severity (CRITICAL 5, ERROR 4, WARNING 3, NOTICE 2) and the request is only denied when the summed inbound score reaches the threshold, which defaults to 5; per-paranoia-level scores are added together before the blocking check. [98]
  • Module 2: writing SecRule virtual patches and staged rollout with DetectionOnly. SecRuleEngine accepts On, Off (the default) and DetectionOnly; in DetectionOnly rules are evaluated and logged but disruptive actions such as deny, drop and redirect are never executed, which is the mechanism for a safe pre-block canary stage. SecRule syntax is SecRule VARIABLES OPERATOR [ACTIONS], with rule actions merged over the default action list. [99]
  • Module 3: deploying virtual patches on NGINX WAF. NGINX App Protect WAF is now branded F5 WAF for NGINX; it can be installed on VMs or bare metal, Kubernetes, Docker and air-gapped environments, and its policies combine attack signatures, bot signatures, threat campaigns, response and server-technology signatures plus user-defined signatures, with separate guidance for signature updates.   • Module 4: prioritizing CVEs with the KEV catalog. CISA describes the KEV catalog as the authoritative list of vulnerabilities exploited in the wild (about 1,760 entries at time of access), publishes it as CSV and JSON for automation, and tells organizations to use it as an input to their vulnerability-management prioritization alongside vendor mitigations and asset internet-exposure assessment. [102]
  • Module 5: SLA-driven approval and remediation timelines.
