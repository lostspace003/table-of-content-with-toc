Course outline

Troubleshooting Automation with Claude

From ServiceNow acknowledgement to reason, action and next action

3 days (8 hours per day) Intermediate Instructor-led, hands-on labs Capstone project

About this course

Who should attend

Network operations, load balancer and data centre engineers, NOC and service desk teams, IT automation leads in India and worldwide.

Prerequisites

  • Basic networking and load balancer concepts (VIP, pool, HA)
  • Comfort with a CLI such as F5 tmsh or NetScaler shell
  • Basic Python and Git
  • Familiarity with ServiceNow incidents is helpful, not required

What you will be able to do

  • Explain the incident-to-resolution workflow in ServiceNow and where an agent can and cannot act
  • Set up Claude Code, the Claude Agent SDK and MCP servers scoped to incident triage with read-only tools by default
  • Pull incidents through the ServiceNow Table API, draft the acknowledgement mail and ask for the primary troubleshooting details that are missing
  • Collect typed evidence from F5, NetScaler, Radware, other load balancers (Anaya LB) and Cisco ACI and have Claude suggest ranked CLI troubleshooting steps as structured JSON
  • Enforce read-only versus state-changing command classes, human approval and a full audit trail into ServiceNow work notes
  • Generate and post the reason, action and next action template and ship a tested troubleshooting page

Engineering principles used throughout

  • Model output is a proposal, not a fact: every finding and generated change is validated by deterministic checks and tests.
  • Authorization lives outside the model: tool access is enforced by application code, scoped credentials and policy.
  • Human approval for consequential actions: deploying a mitigation, changing production configuration, rotating credentials.
  • Decisions, evidence, model and tool versions, approvals and outcomes are logged without recording secrets.
  • A model adapter and a tool adapter layer keep every build provider-agnostic and enterprise-portable.
  • Quality is measured: false positives, false negatives, reliability, latency, cost and safe failure, not just a demo.
