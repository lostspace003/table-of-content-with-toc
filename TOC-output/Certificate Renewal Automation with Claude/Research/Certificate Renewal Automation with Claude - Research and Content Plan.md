# Certificate Renewal Automation with Claude: Research and Content Plan

Network and Infrastructure Automation · 3 days (8 hours per day) · Intermediate · Compiled 30 October 2026

This document is the working plan for building the course from its outline. It records where the course came from, why the outline is shaped the way it is, what goes into every module (lessons, teaching points, demo, lab, pitfalls and knowledge checks), the lab environment to prepare, and the sources behind each fact. Numbers in square brackets point to the reference list at the end; every URL there was opened and checked against the fact it supports.

## 1. Where this course came from

**Client input.**

> Client use case 1, 'Certificate Update Automation': "Certificate update by automation for all kinds of load balancer devices: F5, NetScaler, Radware, Anaya LB." The client's stated aim for all use cases is "to do automation using Claude for all these content" with titles on the line of "Automation of <> using Claude".

Expired certificates are one of the most avoidable causes of outages on load balancers, and renewal is about to become much more frequent. The CA/Browser Forum Baseline Requirements cut the maximum validity of publicly trusted TLS certificates from 398 days to 200 days in March 2026, 100 days in March 2027 and 47 days in March 2029 [18]. A team that renews a few hundred certificates by hand once a year will soon be doing it several times a year on every load balancer they own.

The hard part is not getting a certificate; ACME already automates issuance [5]. The hard part is putting it on the right objects on each platform: F5 certificate and key files referenced from client-ssl profiles [1][10], NetScaler cert-key pairs bound to every SSL virtual server [3], Alteon certificates applied through a separate step [4], and HA pairs that must be synchronized [13]. Each platform has its own API and its own failure modes.

This course teaches teams to use Claude where it helps most (reading inventory, drafting plans and code, explaining) while keeping every device write in deterministic, tested code behind a human approval. That split follows OWASP guidance on limiting agent permissions and requiring human approval for high-impact actions [28], and it gives the client a pipeline they can audit.

## 2. How the outline was shaped

| Decision | Rationale |
|---|---|
| Cover F5, NetScaler and Radware in depth and Anaya LB through an adapter | The client named all four. F5, NetScaler and Radware have public API documentation [1][2][29]; we could not find public documentation for Anaya LB, so the course builds a shared adapter contract that the client can implement against their own Anaya documentation. |
| Claude plans and drafts; deterministic code executes | Certificate installs touch production traffic. Keeping writes in tested Python, with the model limited to read-only tools, follows OWASP's excessive-agency mitigations [28] and makes behavior repeatable. |
| Start with a manual renewal before any automation | Learners need to see where outages come from (chain, key match, missed binding, HA sync) before they can write checks that catch them. |
| ServiceNow change records and approval as the gate | The client's other use cases already center on ServiceNow (SNOW). Using the Table API [24] and Flow Designer approval [25] fits existing change practice. |
| Keys and CSRs generated by code, never by the model | Private keys must never enter prompts or logs. Generating CSRs in code with a standard library [27] keeps key material out of the model's context. |
| GitHub pull requests and Actions for review and CI | Reviewing renewal plans like code gives a second human view and a test record; scheduling through Actions [26] gives a simple way to run inventory daily. |

## 5. Module-by-module content plan

### Day 1

#### Module 1: Certificate lifecycle on load balancers and the automation baseline

**Goal.** Learners understand exactly where a certificate lives and is bound on each platform, and where manual renewals fail, before any automation is written.

**Outline topics.**

- How each platform stores and binds certificates: F5 client-ssl profiles and virtual servers, NetScaler sslcertkey and sslvserver bindings, Radware Alteon certificate repository and SSL policies, other load balancers (Anaya LB)
- Where renewal outages come from: wrong chain, mismatched key, binding missed on a standby, HA sync skipped
- The operating pattern for the whole course: Claude plans, drafts and explains; deterministic code executes; a human approves; everything is logged
- Lab estate walkthrough: lb-f5-01, lb-ns-01, lb-rw-01, an ACME lab CA and a ServiceNow developer instance

**Learning objectives.**

- Learners can trace a certificate from file object to virtual server on F5, NetScaler and Alteon
- Learners can name the four most common renewal outage causes and show where each happens
- Learners can explain why shorter certificate lifetimes make manual renewal unsustainable
- Learners can state the course operating pattern: Claude plans, code executes, a human approves, everything is logged

##### F5 BIG-IP: files, profiles, virtual servers

- Certificates and keys are separate file objects: /mgmt/tm/sys/file/ssl-cert and /mgmt/tm/sys/file/ssl-key, each keyed by name, partition and subPath [1][14]
- A client-ssl profile references the pair through certKeyChain; the older cert and chain properties are deprecated [10]
- A client-ssl profile needs at least one cert/key pair; tmsh edits it with cert-key-chain add, modify or replace-all-with [11]
- The profile, not the certificate, is attached to the virtual server, so one certificate can sit behind many virtual servers through shared profiles
- Every ssl-cert object exposes expirationDate, subject, issuer, subjectAlternativeName and serialNumber, which is what inventory will read [1]

##### NetScaler: cert-key pairs and vserver bindings

- Files sit in /nsconfig/ssl by default; add ssl certKey creates a named pair that points at the files [3]
- Intermediates must be linked to the server cert-key pair before binding (linkcertkeyname in NITRO) [3][2]
- Each SSL virtual server needs its own binding: bind ssl vserver <vs> -certkeyName <name>, checked with show ssl vserver [3]
- Built-in expiry monitoring exists (expirymonitor, notificationperiod 10 to 100 days) but only alerts; it never renews [2]
- Updating a pair in place (update ssl certKey, NITRO ?action=update) swaps the files under every existing binding at once [2]

##### Radware Alteon and other platforms (Anaya LB)

- Alteon CLI installation: one PEM with server cert then intermediates, entered under cfg then cert, terminated with three periods, then apply [4]
- Configuration changes are pending until applied; treat apply and save as explicit, separate steps in every runbook
- Radware publishes a Python SDK over the Alteon REST backend with an SSL key configurator, which the course uses as the API reference point [29]
- Anaya LB has no public API documentation we could verify; the course treats it through an adapter that the client fills in against their own device documentation

##### Where renewal outages really come from

- Wrong or missing chain: the leaf is valid but clients cannot build a path; openssl s_client -showcerts shows what the server really sends [20]
- Key and certificate mismatch: the object installs but the handshake fails
- Binding missed on one of several virtual servers or SNI profiles, especially where sniDefault decides the fallback profile [10]
- HA pair not synchronized after the change, so the standby still serves the old certificate after failover [13]
- Public certificate lifetimes drop to 200 days from March 2026, 100 days from March 2027 and 47 days from March 2029, so renewals become frequent routine work [18]

##### The operating pattern and the lab estate

- Claude reads, plans, drafts code and explains; deterministic Python performs every device write
- Every write needs an approved change and a named human approver; the agent cannot self-approve [28]
- Lab estate: lb-f5-01 (with a standby peer), lb-ns-01, lb-rw-01, a step-ca ACME lab CA and a ServiceNow developer instance [31][33]
- Everything is logged: prompts, tool calls, device requests and responses, approver and time

**Instructor demo.**

1. Open the F5 GUI and REST side by side; GET /mgmt/tm/ltm/profile/client-ssl/~Common~clientssl_payments and point to certKeyChain
2. GET the referenced ssl-cert object and read expirationString, serialNumber and subjectAlternativeName aloud
3. On lb-ns-01 run show ssl certKey and show ssl vserver vs_portal_443 to show the binding and linked intermediate
4. Run openssl s_client -connect portal.example.corp:443 -servername portal.example.corp -showcerts against both devices and compare chains
5. Renew one F5 certificate by hand and deliberately skip config sync; fail over and show the old serial being served
6. Draw the failure-point map on the whiteboard as learners call out each step

**Hands-on lab.** Renew one certificate by hand on lb-f5-01 and one on lb-ns-01 using a lab CA certificate, writing down every step and every point where a mistake would cause an outage.

1. Request a certificate for pay.example.corp from the step-ca lab CA using the CSR provided
2. On F5, import the key and certificate with date-suffixed names through the GUI or tmsh
3. Update clientssl_payments cert-key-chain to the new pair and confirm with tmsh list ltm profile client-ssl clientssl_payments
4. Run tmsh run cm config-sync to-group <device group> and confirm the peer shows in sync
5. On NetScaler, copy files to /nsconfig/ssl, add the cert-key pair, link the intermediate and bind it to vs_portal_443
6. Verify both with openssl s_client -showcerts and record the new serial numbers
7. Write each step into the runbook template with the time it took
8. Mark every step on the failure-point map with what would go wrong and how you would detect it

**Lab success criteria.**

- Both virtual servers serve the new serial with a complete chain
- The F5 standby holds the same certificate objects after sync
- The runbook lists every step, command and verification
- The failure-point map covers chain, key match, missed binding and HA sync at minimum

**Deliverable.** Manual renewal runbook and failure-point map.

**Common pitfalls.**

- Overwriting the existing certificate object instead of creating a new date-suffixed object, which removes the rollback path
- Forgetting to link the intermediate on NetScaler before binding
- Checking only the active F5 unit and not the standby
- Trusting the browser view of the chain, which may fill gaps from its own cache, instead of s_client -showcerts

**Knowledge check.**

1. On F5, what attaches a certificate to a virtual server? Answer: A client-ssl profile whose certKeyChain references the cert and key objects; the profile is then attached to the virtual server.
2. Why does NetScaler expiry monitoring not solve the renewal problem? Answer: expirymonitor and notificationperiod only raise an alert before expiry; they do not request, install or bind a new certificate.
3. What does openssl s_client -showcerts show that a browser may not? Answer: Only the certificates the server actually sent, in order, without filling in missing intermediates.
4. Why will renewal frequency increase over the next few years? Answer: The CA/Browser Forum Baseline Requirements cut maximum public certificate validity to 200 days in 2026, 100 days in 2027 and 47 days in 2029.

**Slides and assets to prepare.**

- Side-by-side diagram of the object model on F5, NetScaler and Alteon
- Failure-point map template (blank and instructor-completed versions)
- Manual renewal runbook template
- Validity reduction timeline chart from the Baseline Requirements
- Lab estate topology diagram with hostnames

#### Module 2: Setting up Claude Code, the Agent SDK and MCP for certificate work

**Goal.** Learners build a workbench where Claude can read certificate data through narrow read-only tools and cannot change any device.

**Outline topics.**

- Claude Code project setup: CLAUDE.md with estate conventions, naming rules for certificate objects, and what the agent may never do
- Claude Agent SDK in Python: defining tools with JSON schemas, forcing structured JSON outputs, handling tool-use loops
- An MCP server exposing read-only inventory tools (list_certs, get_expiry, get_bindings) and no write tools
- Secrets handling: device credentials in environment variables and a vault, never in prompts or repositories

**Learning objectives.**

- Learners can install Claude Code and write a project CLAUDE.md that encodes estate conventions and red lines
- Learners can define typed tools with the Agent SDK and expose them through an MCP server
- Learners can block unwanted tool calls with permissions and PreToolUse hooks
- Learners can keep device credentials out of prompts, logs and the repository

##### Claude Code and the project file

- Install with curl -fsSL https://claude.ai/install.sh | bash on macOS, Linux or WSL; claude -p runs it non-interactively for scripts and CI [8]
- Project instructions live in ./CLAUDE.md or ./.claude/CLAUDE.md and are shared through source control [30]
- Put naming rules in CLAUDE.md: <fqdn>_<YYYYMMDD> for certificate objects, clientssl_<app> for profiles
- State red lines plainly: never call write endpoints, never read files under secrets/, never print key material
- Keep CLAUDE.md short and specific; long files cost context and reduce adherence [30]

##### Agent SDK tools with schemas

- Define each tool with @tool (name, description, input schema, handler), wrap them with create_sdk_mcp_server and pass them in mcp_servers [22]
- Tool names become mcp__certops__list_certs and must be listed in allowed_tools to run without a prompt [22]
- Mark read tools with readOnlyHint and return machine-readable results in structuredContent alongside text [22]
- Return isError: true with a clear message when a device call fails so the model does not invent data [22]
- The SDK uses API-key authentication for anything you ship to others [9]

##### A read-only certificate MCP server

- Three tools only: list_certs(device), get_expiry(device, cert), get_bindings(device, cert)
- No write tool exists in the server, so a prompt cannot reach a write path
- MCP standardizes how tools are described and called, so the same server works from Claude Code and the Agent SDK [7]
- Each tool returns typed records validated before they are returned

##### Guardrails at the workbench

- PreToolUse hooks run before a tool call and can deny it with a reason; use one to block any Bash call containing curl -X POST, PUT, PATCH or DELETE against device addresses [21]
- Credentials come from environment variables injected from a vault at process start, never from prompts
- Redact Authorization, Cookie and X-NITRO-PASS headers in every log line [2]
- Least privilege on devices too: the read tools use a read-only device account [28]

**Instructor demo.**

1. Create the repo, run claude in it and write CLAUDE.md live with the naming rules and red lines
2. Write list_certs for F5 with @tool, returning name, expirationDate and serialNumber from /mgmt/tm/sys/file/ssl-cert
3. Register the server and show the tool name mcp__certops__list_certs in the session
4. Ask Claude to explain bindings on lb-f5-01 and show it calling only read tools
5. Ask Claude to replace the certificate and show the request refused because no write tool exists and the hook denies device writes
6. Show the log file with secrets redacted

**Hands-on lab.** Build the read-only certificate MCP server, connect it to Claude Code and ask Claude to explain the bindings on lb-f5-01 without changing anything.

1. Clone the starter repo and create a Python virtual environment
2. Write CLAUDE.md with naming conventions, lab hostnames and red lines
3. Implement list_certs, get_expiry and get_bindings for F5 against the recorded responses in fixtures/f5/
4. Add readOnlyHint to every tool and return structuredContent
5. Register the server in Claude Code and confirm the three tools appear
6. Add a PreToolUse hook that denies any shell command sending POST, PUT, PATCH or DELETE to a device address
7. Point the tools at lb-f5-01 using credentials from environment variables
8. Ask Claude which virtual servers depend on pay.example.corp and save the answer

**Lab success criteria.**

- Claude answers using only tool results and names the profile and virtual servers correctly
- A request to change the certificate is refused and the refusal is logged
- No credential appears in the repo, the transcript or the log
- pytest passes for all three tools against recorded responses

**Deliverable.** Working agent workbench with read-only MCP tools.

**Common pitfalls.**

- Exposing a generic run_command tool, which turns a read-only server into a write path
- Putting the device password in CLAUDE.md or a prompt 'just for the lab'
- Returning free text from tools so the model has to guess at field meanings
- Relying on tool annotations alone; MCP treats them as hints, so enforcement must be in code and hooks

**Knowledge check.**

1. What makes a tool callable without a prompt in the Agent SDK? Answer: Listing its full name, mcp__{server}__{tool}, in allowed_tools.
2. Where should the rule 'never call write endpoints' be enforced? Answer: In code: no write tools in the server plus a PreToolUse hook; CLAUDE.md states the rule but is not enforcement.
3. What should a tool return when the device call fails? Answer: isError: true with a clear message, so Claude reports the failure instead of inventing data.

**Slides and assets to prepare.**

- Starter repo with CLAUDE.md template and tool skeletons
- Diagram: Claude Code to MCP server to device, with the read-only boundary marked
- Hook script example that denies device write methods
- Recorded F5 responses for list, expiry and bindings

#### Module 3: Certificate inventory and expiry discovery across platforms

**Goal.** Learners build collectors that turn three different APIs into one typed inventory, with unknowns marked rather than guessed.

**Outline topics.**

- F5 iControl REST: /mgmt/tm/sys/file/ssl-cert, /mgmt/tm/ltm/profile/client-ssl and virtual server lookups; tmsh equivalents for verification
- NetScaler NITRO: /nitro/v1/config/sslcertkey and sslvserver_sslcertkey_binding; Radware Alteon REST API certificate and SSL policy objects; an adapter interface for other load balancers (Anaya LB)
- A typed inventory record: device, platform, certificate name, subject and SANs, chain, expiry, bound virtual servers, owner, confidence
- Claude drafts the collectors; you review the diffs and run pytest against recorded API responses

**Learning objectives.**

- Learners can read certificates, profiles and bindings from F5 iControl REST and NetScaler NITRO
- Learners can map Alteon certificate data through the Radware SDK or REST backend behind an adapter
- Learners can define a typed inventory record with a confidence field
- Learners can review Claude-drafted collector code and test it against recorded responses

##### F5 collection

- GET /mgmt/tm/sys/file/ssl-cert returns every certificate with expirationDate, subjectAlternativeName, issuer and serialNumber [1]
- GET /mgmt/tm/ltm/profile/client-ssl returns certKeyChain entries that map profiles to cert and key names [10]
- Map profiles to virtual servers by reading each virtual server's profiles list; verify a sample with tmsh list ltm profile client-ssl [11]
- Collect partitions explicitly; objects outside /Common are easy to miss

##### NetScaler collection

- Log in with POST /nitro/v1/config/login and send Cookie: NITRO_AUTH_TOKEN on later calls [2]
- GET /nitro/v1/config/sslcertkey returns pairs with daystoexpiration and linked CA pair names [2]
- GET /nitro/v1/config/sslvserver_sslcertkey_binding/<vservername> returns the certkeyname and whether it is an SNI or CA binding [15]
- Use ?count=yes to check totals before paging through large estates [2]

##### Alteon and the adapter interface

- The Radware alteon-sdk reads SSL keys and certificates through configurators over the REST backend; it requires Alteon 31.0.10.0 or 32.2.2.0 at minimum [29]
- Wrap every platform behind one interface: list_certificates(), list_bindings(), device_facts()
- The Anaya LB adapter is a stub that returns UNKNOWN for every field until the client supplies its API details
- Adapters normalize dates to UTC and serials to uppercase hex so rows compare across platforms

##### The typed inventory record

- Fields: device, platform, cert_name, subject, sans, issuer, serial, not_after, chain_complete, bound_to, owner, confidence
- confidence is high when the binding was read from the device, low when inferred, unknown when the source is missing
- Owner comes from CMDB; a missing owner is recorded as UNKNOWN, never filled in by the model
- Every row carries an ID such as inventory#f5-0031 so later plans can cite it

##### Claude drafts, you review

- Ask Claude to draft each collector from the API reference and a recorded response
- Review the diff line by line; reject any write call or unbounded retry
- Test with pytest against recorded JSON; monkeypatch the HTTP client so tests never touch a device
- Ask Claude to explain each field mapping and compare the explanation to the API reference

**Instructor demo.**

1. Show raw JSON from F5 ssl-cert, client-ssl and a virtual server, and the joins needed between them
2. Show raw NITRO sslcertkey and sslvserver_sslcertkey_binding responses for lb-ns-01
3. Prompt Claude to draft the NetScaler collector and review the diff aloud, rejecting one unsafe change
4. Run pytest against recorded responses and show a failing test caught by a missing field
5. Generate the expiry report and point out rows marked UNKNOWN

**Hands-on lab.** Build the multi-platform inventory collector and produce one expiry report for the lab estate with unknowns marked explicitly.

1. Define the inventory record as a dataclass or Pydantic model with the fields above
2. Ask Claude to draft the F5 collector; review and commit it
3. Ask Claude to draft the NetScaler collector including login and bindings; review and commit it
4. Implement the Alteon adapter against recorded responses
5. Add the Anaya LB stub that returns UNKNOWN
6. Write pytest cases for each collector with recorded responses
7. Join owner data from the ServiceNow CMDB export fixture
8. Produce expiry_report.csv and expiry_report.md sorted by not_after

**Lab success criteria.**

- Every certificate on the three lab devices appears once with its bindings
- Rows with a missing owner or unverified binding are marked UNKNOWN or low confidence
- All collector tests pass without network access
- The report shows pay.example.corp bound to vs_payments_443 on lb-f5-01

**Deliverable.** Certificate inventory and expiry report.

**Common pitfalls.**

- Assuming certificate name equals hostname; match on SANs instead
- Missing SNI bindings or non-Common partitions
- Letting the model fill in a missing owner from the hostname
- Tests that call a live device and pass only when the lab is up

**Knowledge check.**

1. Which NITRO resource tells you which virtual servers use a cert-key pair? Answer: sslvserver_sslcertkey_binding, read per virtual server.
2. Why does each inventory row carry an ID? Answer: So the planning agent can cite exact rows as evidence and reviewers can check them.
3. What should the collector do when it cannot read a binding? Answer: Record the field as unknown with low confidence; never infer it silently.

### Day 2

#### Module 4: Renewal planning agent and ServiceNow change records

**Goal.** Learners build an agent that turns inventory into a cited JSON renewal plan and a ServiceNow change, with code, not the model, handling keys and CSRs.

**Outline topics.**

- Planning agent: group certificates by expiry window, owner and platform; propose order, maintenance window and blast radius as structured JSON
- Mandatory citations to inventory rows; unknowns (missing owner, unverified binding) block the plan instead of being guessed
- Opening and updating change_request via the ServiceNow Table API; triggering an approval path in Flow Designer
- Requesting the new certificate from the ACME lab CA or an internal CA request with CSR generated by code, not by the model

**Learning objectives.**

- Learners can force the planning agent to return a plan that matches a JSON schema
- Learners can make unknowns block a plan rather than be guessed
- Learners can create and update change_request records through the Table API and route them to approval
- Learners can generate keys and CSRs in code and obtain certificates from an ACME lab CA

##### Plan schema and structured output

- Define the plan schema: steps[], each with device, cert, target_objects, window, blast_radius, evidence[] and rollback
- Send the schema in output_config.format so the response matches it; use strict tool use for tool inputs [23]
- Validate the plan again in code before anything else reads it
- Order by expiry first, then blast radius (number of virtual servers and business service)

##### Citations and blocking unknowns

- Every step must cite inventory row IDs; the validator rejects steps without evidence
- Any cited row with owner UNKNOWN or binding confidence low turns the plan status to BLOCKED with a reason
- The agent may explain why a plan is blocked; it may not change the inventory to unblock it
- A blocked plan is still saved and shown, so the owner gap becomes a visible task rather than a silent skip

##### ServiceNow change records

- Create with POST /api/now/table/change_request (one record per call, 201 on success) [24]
- Update with PATCH /api/now/table/change_request/{sys_id}; read state with GET and sysparm_fields to keep payloads small [24]
- Put the plan summary, evidence row IDs and rollback command in the description and work notes
- Use a Flow Designer flow with Ask for Approval on the change record; read the resulting approval state rather than assuming it [25]
- Give the approval a due date so a forgotten request resolves instead of waiting forever [25]

##### Keys, CSRs and the ACME lab CA

#### Module 5: Deterministic executor: F5 BIG-IP with iControl REST and tmsh

**Goal.** Learners build and test an F5 executor that installs a new certificate as new objects, swaps the profile, syncs the HA pair and verifies, with no model in the write path.

**Outline topics.**

- Upload key and certificate through /mgmt/shared/file-transfer/uploads, then create sys file ssl-key and ssl-cert objects
- Update the client-ssl profile cert-key-chain and confirm virtual server bindings; verify with tmsh list ltm profile client-ssl
- Idempotency, naming with date suffixes, and config sync across the HA pair before declaring success
- pytest with recorded iControl responses; Claude drafts code, explains each call, and never holds the credentials

**Learning objectives.**

- Learners can upload files to BIG-IP through the file-transfer worker with chunking

- Learners can make the executor idempotent and HA-aware
- Learners can test the executor against recorded iControl responses

##### Uploading files

- POST /mgmt/shared/file-transfer/uploads/<filename> writes to /var/config/rest/downloads/ [12]
- Send Content-Range: start-end/filesize; files over 1M must be sent in chunks [12]
- Upload the key and certificate as separate files and remove them from the downloads directory after import
- Check the upload response for the final byte count before creating objects

##### Creating objects and swapping the profile

- Create the key at /mgmt/tm/sys/file/ssl-key and the certificate at /mgmt/tm/sys/file/ssl-cert with sourcePath file:/var/config/rest/downloads/<file> [14][1]
- Name objects <fqdn>_<YYYYMMDD> so the previous object stays for rollback
- PATCH /mgmt/tm/ltm/profile/client-ssl/~Common~<profile> with the new certKeyChain entry (cert, key, chain) [10]
- Verify with tmsh list ltm profile client-ssl <profile> cert-key-chain [11]

##### Idempotency and HA

- Before each write, read the current state; if the target object already exists with the same serial, skip
- Record state after each step so a rerun continues from the last completed step
- Run cm config-sync to-group for the device group and read sync status before reporting success [13]
- Never write to the standby; writes go to the active unit and reach the peer through sync

##### Testing and the model's role

- pytest with recorded iControl responses for every call, including error responses
- Contract tests: a plan step in, a result with request IDs and evidence out
- Claude drafts and explains each call; the executor runs under a service account whose credentials Claude never receives
- Dry-run mode prints the exact method, URI and redacted body for every planned call

#### Module 7: Guardrails, approvals and audit for certificate changes

**Goal.** Learners build a policy module that refuses any install without an approved change, open window, allowed device and healthy HA, and an audit trail that proves it.

**Outline topics.**

- Policy checks before any write: approved change in ServiceNow, maintenance window open, device on allow list, HA healthy and in sync
- Human approval gate: the approver sees the plan, the diff of bindings and the rollback command; the agent cannot self-approve
- Scope limits: the model proposes, executors refuse anything outside the plan, and credentials never pass through Claude
- Audit log of prompts, tool calls, device responses, approver and timestamps; evidence attached back to the change record

**Learning objectives.**

- Learners can implement pre-write policy checks against ServiceNow and device state
- Learners can present an approver with plan, binding diff and rollback command
- Learners can ensure the model proposes but cannot approve or execute outside the plan
- Learners can write an audit log and attach evidence to the change

##### Policy checks before any write

- Change approved: read the change_request and its approval through the Table API [24]
- Window open: compare now with the change's planned start and end
- Device on the allow list for this change; anything else is BLOCKED
- HA healthy and in sync on F5 and NetScaler before writing [13]
- Each check returns PASS or BLOCKED with a reason that is logged

##### The human approval gate

- Use Ask for Approval on the change record; branch on Approved and treat every other state as no [25]
- The approval view shows the plan, the before-and-after binding diff and the exact rollback command
- The agent's service account has no approval rights, so it cannot approve its own plan
- OWASP recommends human approval for high-impact actions and minimal permissions for agent tools [28]

##### Scope limits

- Executors check every step against the approved plan hash and refuse anything else
- Hooks block the model from calling executors directly from a chat session [21]
- Credentials are injected into executors at run time and never reach Claude
- Least privilege on devices: executor accounts can manage SSL objects but not users, routing or licensing [28]

##### Audit trail

- Append-only JSON lines: prompt, tool calls, plan hash, approver, timestamps, device requests and responses
- Attach the evidence bundle to the change record with a work note via PATCH [24]
- Audit entries carry the change number so they can be retrieved per change
- Store the log outside the executor host's write path, for example shipped to a log platform as it is written

- No path exists for the agent to approve its own change

**Common pitfalls.**

- Checking approval once at plan time and not again at execution time
- Time zone mistakes when comparing the window
- Treating Requested or Skipped as approved
- Logs that can be edited after the fact

#### Module 8: Pre- and post-checks, rollback and the GitHub pipeline

**Goal.** Learners prove every renewal with handshake, chain and serial checks, roll back automatically on failure and ship renewals through pull requests and Actions.

**Outline topics.**

- Pre-checks: current TLS handshake per virtual server, chain validation, key-certificate match, HA sync status
- Post-checks: new serial served on every virtual server, OCSP and chain valid, no handshake errors; automatic rollback to the previous object on failure
- GitHub pull request per renewal plan with Claude-written summary; GitHub Actions runs pytest, the dry run and the post-check report
- Scheduling renewals ahead of expiry and reporting to the certificate owner

**Learning objectives.**

- Learners can write pre- and post-checks for handshake, chain, key match, OCSP and serial
- Learners can implement automatic rollback to the previous object
- Learners can run tests, dry run and post-check reports in GitHub Actions
- Learners can schedule renewals ahead of expiry and report to owners

##### Pre-checks

- Handshake per virtual server with openssl s_client -connect host:443 -servername <fqdn> [20]
- Chain validation with openssl verify -CAfile root.pem -untrusted intermediates.pem leaf.pem [6]
- Key and certificate match by comparing public keys in code before upload
- HA sync status on both pair members

##### Post-checks and rollback

- New serial served on every bound virtual server and on each HA member after failover test
- OCSP status good with s_client -status where stapling is enabled [20][19]
- Any failure triggers rollback: re-point the profile or binding to the previous date-suffixed object and sync
- Rollback is itself verified with the same post-checks

##### GitHub pull requests and Actions

- One pull request per renewal plan; Claude writes the summary from plan.json and the evidence
- Actions runs pytest, the dry run and attaches the post-check report as an artifact
- claude -p can generate the summary in CI [8]
- Merging the pull request is not the approval; the ServiceNow approval still gates the install

##### Scheduling and reporting

- A schedule workflow runs inventory daily; schedules run in UTC on the default branch and can be delayed at the top of the hour, so pick an off-peak minute [26]
- workflow_dispatch with inputs lets an operator start a renewal run for one change [26]
- Renew well ahead of expiry; with 47-day certificates from 2029 the planning window shrinks to days [18]
- Send the certificate owner the report with serial, expiry, devices and change number
